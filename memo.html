Code is the assembly. Review the intent.

An engineer opens a pull request. Claude wrote most of the code.

The diff is clean. The implementation looks well-structured. Tests pass. She reviews it for five minutes and approves it.

Three weeks later, there's a production bug.

She traces it back to a constraint established early in the coding session: a strict latency budget for the request. That constraint shaped everything the agent did afterward: the retry strategy, the timeout values, the fallback behavior, the alternatives it rejected along the way. None of that made it into the pull request. The reviewer saw the code. She didn't see the decision that produced the code.

The context had been there. It had mattered. It had shaped the implementation. But by the time the change reached review, the only durable artifact was the diff. Everything upstream of it had become invisible.

This is not a documentation failure. It is a structural consequence of how agents produce code, and understanding it requires starting from a more basic question: what kind of artifact is a diff, and what has it historically represented?

For most of software history, source code was the closest artifact to where decisions were made.

When a developer wrote a function, the code was nearly continuous with the reasoning that produced it. The abstraction chosen reflected what the author expected to vary. The control flow reflected how they modeled the problem. The things commented out reflected the alternatives they considered and rejected. A skilled reviewer reading the diff was, in a meaningful sense, reading a compressed trace of the author's thinking.

This is why code review works at all. Not because reviewers can verify every property of a system from a diff, but because the diff has historically been close enough to the source of the decisions that a reviewer could reconstruct what they needed to.

Coding agents break that proximity.

An engineer tells the agent what needs to happen. The request must stay under 500 milliseconds. This service cannot be called synchronously. Prefer graceful degradation over hard failure. The agent then explores the system and turns those constraints into hundreds of smaller decisions: chooses a timeout, evaluates retry strategies, finds an architectural boundary and routes around it, tries an approach, discovers a test fails, revises its model of the system, and chooses another path.

Intent and constraints go in. Code comes out.

The relationship between the diff and the decisions that produced it is now the same as the relationship between a compiled binary and the source that produced it. You can read the output. You cannot read the reasoning. The important decisions happened upstream, in a process that completed before review began.

That is what “code is the assembly” means. Not literally. Source code is not machine code, and an agent is not a compiler in the formal sense. The point is that the abstraction boundary has moved. When humans write code, the diff is close to the decision. When agents write code, the diff is downstream of it.

And we are reviewing software as though that shift has not occurred.

The reason this matters more than a documentation problem is that traditional code review had a fallback when the diff wasn't enough: you asked the author.

Why did you do it this way? Did you consider making this asynchronous? Why is this timeout 200 milliseconds?

The author might have forgotten. The answer might have been imperfect. But there was always some path back toward the decision: a commit message, a Slack thread, or the author's ability to re-derive from memory.

I probably did it this way because of X.

Human reasoning persists outside the artifact it produced. The author exists after the code is written.

Agent-written code removes that fallback entirely.

An agent makes dozens of consequential decisions inside a session without any of them becoming durable artifacts. The final code records which implementation won. It does not record what alternatives were considered, what constraints eliminated them, or what assumptions made the chosen approach reasonable. The reviewer receives the end of the process without having seen the process. And when they want to ask why, there is no one to ask. The agent has no memory of the session. The reasoning existed inside a context window, and when the session closed, it closed with it.

The distinction is worth being precise about. Context has always been lost in software development. Humans forget, documentation goes stale, the engineer who made a decision leaves the company. What changes with agents is not that context is sometimes lost. It is that the normal recovery mechanisms no longer exist. With human-written code, losing context meant friction. With agent-written code, losing context means the context is gone.

Three categories of missing context recur often enough to be worth naming.

The first is trade-offs considered and rejected. An agent implementing retry behavior evaluates exponential backoff with jitter, ordinarily a reasonable design. But a latency budget established earlier in the session makes worst-case delay unacceptable, so the agent rejects it and chooses a single bounded retry followed by immediate fallback. The reviewer sees an implementation that looks overly conservative and asks why exponential backoff wasn't used. The objection is reasonable from the code alone. It also reopens a decision that was already made correctly, for a constraint the reviewer doesn't know exists.

The second is assumptions about the system. An agent writes a query under the assumption, inferred from context established earlier in the session, that a particular table will remain small. The assumption is never stated. It shapes the implementation, ships with it, and disappears with the session. Months later the table grows tenfold. The query degrades badly. The implementation may have been entirely defensible under the assumptions available at the time. The problem is not that the assumption was wrong. It is that the assumption was never durable. It lived long enough to shape the code but not long enough to warn the engineer who inherited it.

The third is constraints navigated. A prior architectural decision established that a particular internal service must never be called synchronously from a customer-facing request path. The agent encounters that constraint while exploring the codebase and correctly designs around it. The reviewer sees the resulting implementation. They do not see the boundary the agent had to preserve. The agent happened to navigate it correctly. But the reviewer was never in a position to verify that navigation, because the constraint was absent from everything being reviewed.

In each case the structure is the same. The reasoning was real. It shaped the implementation. The implementation survived the session. The reasoning did not.

The compounding effect of this pattern is what makes it a structural problem rather than an occasional inconvenience.

Technical debt is the future cost of implementation decisions. Agent-driven development creates an analogous liability: the future cost of losing the context required to understand those decisions. Call it comprehension debt: the gap between what a system does and what the organization can explain about why it does it that way.

Comprehension debt has always existed in mature codebases. Every engineer has encountered a conditional no one wants to delete because no one remembers what it was protecting. What changes with agents is not the existence of that debt but the rate at which it accumulates.

An agent can traverse a codebase, evaluate approaches, navigate constraints, and produce a working implementation far faster than a human could author the same change. That speed is precisely the value. But implementation throughput can now grow much faster than organizational understanding. A team shipping dozens of agent-written pull requests each week, each locally correct, each passing review, leaves behind a compounding residue of decisions that exist in code and nowhere else.

The cost appears later, and it appears repeatedly. An engineer debugging the system reconstructs a decision that already happened once. A reviewer relitigates an alternative the agent had already ruled out. A maintainer removes a constraint-dependent workaround because the constraint is no longer visible anywhere. An incident responder discovers that a timeout everyone assumed was arbitrary was in fact protecting a latency budget no one knew was still active.

The organization pays again for reasoning it already performed. The agent did the work. The work did not survive in a form that could be used.

The instinct is to save every session. This is correct as far as it goes, and does not go far enough.

A coding session contains thousands of tokens of prompts, tool calls, file reads, failed attempts, and corrections. Somewhere inside that trace is the sentence that explains why the timeout is 200 milliseconds. A reviewer should not need to read the full session to find it. More importantly, they will not. The transcript is an execution trace. It is not a review interface. Asking a reviewer to locate the relevant context inside a raw session log is the same category of problem as asking an engineer to understand a compiled binary by reading its intermediate compilation states. The information is technically present. It is at the wrong level of abstraction.

The question is not whether to preserve session context. It is what form that context needs to take to be usable at the moment review actually happens.

The answer is specific. What needs to survive is not a summary of the session but the context immediately surrounding consequential decisions: what the code at a given line was trying to accomplish, what constraint shaped the choice, what alternative was considered and why it was rejected, what assumption the implementation depends on. Those are the pieces that change what a reviewer can do.

Consider what changes when they are present.

The reviewer reaches this line:

requestTimeout = 200ms

The diff tells them what changed. A Witness annotation tells them why: the request must remain below 500 milliseconds; the agent considered a longer timeout with multiple retries but worst-case execution exceeded the budget; it chose 200 milliseconds, one bounded retry, and immediate fallback.

That context changes the review completely. The reviewer can now challenge the latency budget itself. They can verify the calculation. They can argue the fallback behavior is wrong. They can identify a constraint the agent failed to account for. They can decide the trade-off was made incorrectly.

Without it, the reviewer is attempting to evaluate a decision by reading only its output. With it, they are evaluating the decision. The distinction is not subtle. The first produces merge permission. The second produces review.

The intervention required is also smaller than it might appear. This does not require a new workflow or a new interface. It requires that the context which shaped code at a given line appear at that line, inside the pull request where the reviewer is already working.

The pull request became the center of software review for a simple reason: it put the important artifact in front of the people responsible for deciding whether it should enter the system. That logic still holds. What has changed is what the important artifact is.

When humans wrote the code, the diff was the artifact closest to the decisions. Reviewing the diff meant reviewing the decisions. That is no longer reliably true. If agents increasingly sit between engineering intent and implementation, the context that crossed that boundary needs to be reviewable too, not in a separate system, not reconstructed after the fact, but at the line in the diff where the decision materialized.

The diff shows what changed. The session should show why it became that change.

That is what Witness does. It captures the decision context from coding sessions and surfaces it inside the pull request, at the code it shaped. Not a log of everything the agent did. Most of that does not belong in review. The decisions that would otherwise require rediscovery: the constraint that was navigated, the alternative that was rejected, the assumption the implementation depends on.

The case for this is not that agent-written code is worse than human-written code. It may be better in most respects that are currently measurable. The case is that code, as an artifact, has become less complete as a record of the decisions that produced it. The source of engineering reasoning has moved upstream. The diff is increasingly downstream of where the important choices were made.

Reviewing the diff, and only the diff, means reviewing the assembly.
